# Step 32 - 구현 파일 인덱싱 (tokei)

## 목표

선택된 설계를 구현 가능한 파일·Class·함수 단위로 바꾸고, 신규와 수정 범위 및 의존성
순서를 하나의 bounded 인덱스에 고정한다. 측정 도구의 유무를 구현 계획의 성공과
혼동하지 않는다.

## 입력과 산출물

- 입력: `step_archive/step030_레이아웃설계_chunk1.md`
- 입력: `step_archive/step030_전체설계_chunk1.md`
- 입력: `step_archive/step031_환경준비.md`
- 필수 선행 항목: `step030`, `step031`
- 산출물: `step_archive/step032_파일인덱스_chunk1.md`
- 네트워크: 사용하지 않는다.
- 시각 검토: 필요하지 않다.

## 실행 역할

가능한 경우 파일 인덱스 작성자 역할과 파일 인덱스 독립 검증자 역할을 서로 나눈다.
작성자는 설계를 파일 단위로 분해하고, 독립 검증자는 작성 산출물을 수정하지 않는다.
위임 기능을 사용할 수 없으면 현재 실행자가 두 역할을 명확히 분리해 순서대로 수행하고,
별도 역할을 위임했다고 기록하지 않는다. 정상 권한 확인을 유지하고 자동 승인이나 권한
우회를 금지한다.

## 파일 인덱스 작성

두 설계 청크의 구성 요소마다 파일 경로, Class, public·private 함수, 신규 또는 수정
구분, 직접 의존성과 구현 순서를 적는다. 기존 파일은 관련 symbol과 필요한 범위만
확인하고, 새 파일은 설계의 책임과 경계를 근거로 경로를 정한다. 각 독립 작업 단위에는
1~3개 파일만 배정하고 소유권이 겹치지 않게 한다.

로컬 `tokei`는 선택 사항이다. 이미 실행 가능한 경우에만 파일별 언어와 줄 수를
측정한다. 없으면 `SKIP`과 이유를 기록하고, 안전한 파일 열거와 바이트에서 계산한 줄 수를
결정적 대안으로 사용한다. 새 package나 원격 실행은 허용하지 않는다. 측정 방식과 관계없이
500줄 이상 파일을 표시하고 그 파일은 symbol 위치 중심의 부분 확인 계획을 둔다.

`step_archive/step032_파일인덱스_chunk1.md`는 500줄 이하로 유지한다. manifest에는
설계 입력 digest, 측정 방식과 시각, 행 수, 줄 수를 기록한다. 각 행은 설계 요구 ID,
파일과 symbol, 신규·수정 구분, 1~3개 파일 work unit, 선행 work unit, 테스트 위치를
포함하며 의존성 순서로 정렬한다. 선언되지 않은 추가 청크는 만들지 않는다.

## 독립 검증

독립 검증자는 선택 설계의 모든 구성 요소가 정확히 한 행에 추적되는지, 파일 소유권이
겹치지 않는지, 의존성 순서가 닫혀 있는지, 줄 수와 500줄 경계가 실제 측정 근거와
일치하는지 확인한다.

## 완료 조건

- `implementation-file-index`: bounded 파일·Class·함수 인덱스가 존재한다.
- `selected-design-traceability`: 모든 파일과 symbol이 선택 설계에 추적된다.
- `bounded-file-ownership`: work unit당 1~3개 파일이며 청크가 500줄 이하이다.
- `optional-tokei-disposition`: 로컬 측정 또는 이유 있는 `SKIP`과 대안이 기록됐다.
- `dependency-order`: 신규·수정 파일이 구체적인 의존성 순서로 정렬됐다.

인덱스와 검증 결과를 수락 증거로 제출하고 현재 단계에서 멈춘다. workflow 상태와
영수증만이 이후 진행을 소유한다.

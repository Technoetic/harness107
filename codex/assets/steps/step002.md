# Step 2 - 프로젝트 분석 및 Context 전략 수립

## 목표

프로젝트 규모와 구조를 파악하고, 이후 작업에서 사용할 Context 운용 전략을
500줄 이하 청크로 기록한다. 이 단계는 로컬 파일만 조사하며 네트워크를 사용하지
않는다.

## 입력과 산출물

- 입력: `step_archive/TOPIC/TOPIC.md`
- 입력: `step_archive/step001_preflight.md`
- 필수 선행 항목: `step001`
- 정적 산출물: `step_archive/step002_context전략_chunk1.md`
- 시각 검토: 필요하지 않다.

## 1. 조사 질문

조사 전에 한 문장씩 답하고 결과 청크에 포함한다.

- 프로젝트 분석의 핵심 목적은 무엇인가?
- 분석 결과가 이후 작업에 어떤 결정을 제공하는가?
- 반드시 확인할 구조, 규모, 위험 항목 세 가지는 무엇인가?

## 2. 프로젝트 규모 기록

프로젝트 경계 안에서 파일 목록과 디렉터리 구조를 조사한다. 생성물, 의존성 캐시,
버전 관리 내부 자료는 규모 계산에서 분리한다. 최소한 다음 정보를 기록한다.

- 전체 관련 파일 수와 주요 확장자별 수
- 주요 디렉터리와 역할
- 줄 수가 큰 관련 파일과 예상 조사 비용
- 사용 중인 언어, 빌드 방식, 테스트 방식
- 주제 파일 및 프리플라이트 결과가 주는 제약

500줄 이상 파일은 전체 로딩보다 검색과 필요한 범위 확인을 우선한다. 이미 확인한
내용은 청크에 요약해 불필요한 반복 로딩을 줄인다.

## 3. Context 전략

다음 기준을 출발점으로 작업 단위를 정하되 실제 사용 가능한 병렬 용량을 넘지
않는다.

- 관련 파일 1,000개 이상: 조사 단위를 20개 이상으로 세분화
- 관련 파일 100개 이상 1,000개 미만: 조사 단위를 10~20개로 세분화
- 관련 파일 100개 미만: 조사 단위를 5~10개로 세분화
- 핵심 작업 집합: 한 번에 10개 이하의 파일
- 개별 조사 단위: 한 번에 1~5개의 파일

복잡한 조사 항목은 서로 독립적인 단위로 나누고, 사용할 수 있는 병렬 용량 안에서
진행한다. 핵심 작업 집합이 과도하게 커지기 전에 남은 조사 항목을 새 단위로
분리한다.

## 4. 청크와 manifest

첫 결과는 반드시 `step_archive/step002_context전략_chunk1.md`에 저장한다. 내용이
500줄을 넘으면 아래 규칙으로 추가 청크를 만든다.

```text
step_archive/step002_context전략_chunk2.md
step_archive/step002_context전략_chunk3.md
```

`chunk1`의 `Chunk manifest` 절에는 `chunk1`을 포함한 모든 청크의 정확한 상대 경로,
줄 수, 다루는 항목을 표로 기록한다. 모든 청크는 각각 500줄 이하여야 하며 병합하지
않는다. 추가 청크는 동적 산출물이므로 index의 정적 산출물 목록에는 넣지 않는다.

## 완료 조건

- `context-strategy-chunk-1`: 첫 청크와 추가 청크 manifest가 존재한다.
- `project-scale-recorded`: 파일 수, 큰 관련 파일, 구조와 도구 방식이 기록되어 있다.
- `context-chunks-bounded`: manifest의 모든 청크가 실제로 존재하며 각각 500줄 이하이다.

검증 결과를 수락 증거로 제출하고 이 단계에서 멈춘다.
